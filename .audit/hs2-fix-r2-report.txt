Repair and commit contract
Data shape remains ResolutionSource with the full captured pairing, role and lifecycle generation. Committed settings own endpoint state. Visible pairing is a projection of that authority.

1. Before the settings transform accepts an endpoint, the original resolution context must still be active, the full settings pairing/role must equal the captured source, and generation/visible role/enabled state must still match. A cancelled resolution waiting for settings cannot gain authority from NonCancellable.
2. An accepted settings commit completes persistence and effective settings publication in NonCancellable. Lifecycle invalidation is still immediate. An invalidation after acceptance may leave that already-accepted endpoint saved for the same pairing, but cannot authorize transport continuation. A result invalidated before the transform cannot persist an endpoint. This is the commit boundary, not a retry workaround.
3. finally reconciles visible pairing from the latest authoritative settings even when the callback fails or resolution is cancelled. It does not copy a stale discovered endpoint over a replacement pairing. Hub-port normalization is shared with hydration and source matching.
4. Hub pairing, client re-pair and unpair now reconcile via the same short resolutionLock rather than writing independent visible values outside it. Hydration invalidation plus publication also holds this short lock. A late discovery reconciliation cannot win over an independently written replacement value between a settings read and visible publication.
5. After reconciliation, cancellation is checked again. Continuation requires the committed endpoint's full source identity, generation, enabled state and role to remain current. Stopped, disabled, replaced or cancelled foreground work does not start sync. A later explicit sync uses the committed endpoint and succeeds.

Lock order: AppContainer settingsMutex -> synchronous transform -> short resolutionLock. Reconciliation acquires resolutionLock and reads only the published StateFlow snapshot through settings(); it never acquires settingsMutex or the transport mutex. No resolutionLock monitor spans a suspension, persistence, network operation or transport-mutex acquisition. The sync transport mutex may enclose a settings commit, as before. No settings transform or reconciliation acquires the transport mutex. Service hydration uses the same short publication lock. No new mutex or lifecycle flag was added.

Alternative considered: serialize lifecycle changes and discovery commit under a new suspend mutex. Rejected because hydration is synchronous and stop/invalidation must remain immediate; nested transport locking would need a broader rewrite.
