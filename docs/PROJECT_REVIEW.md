Project review, 6 September 2026

Spotify startup and playback state deserve attention before more provider features. This review covers the working tree, including the new browser-based Spotify player. Other edits and commits arrived during the review, so the findings refer to the files inspected here, not just the last commit.

The library failure was reproduced with a playlist whose `images` field is null. The corrected loader subsequently read 1,721 liked songs and 14 playlists from the configured account. The permanent regression fixture contains no account data; the temporary live-account test has been removed. Liked songs and playlists now retain successful results independently.

Changes made during the playback review:

- Preserve `ActivationRequired` after the SDK reports `autoplay_failed`. Previously, a recent heartbeat let the next play request overwrite this with `Ready`.
- Report the browser's successful Enable Audio action back to the host before using that device again.
- Invalidate the remembered device after SDK errors such as `not_ready`.
- Transfer playback to a newly registered web device before requesting the track. SDK registration alone does not establish which Connect device is active.
- Propagate cancellation from web-player startup instead of trying another device after the user has cancelled.

The latest runtime logs showed successful SDK registration, browser autoplay rejection, and repeated playback HTTP 404 responses. Tests reproduce the activation-state bug and the missing transfer. These fixes have not yet been verified by an audible cold-start playback test. Spotify documents readiness, autoplay activation, disconnection, and playback-state events separately in its [Web Playback SDK reference](https://developer.spotify.com/documentation/web-playback-sdk/reference), and exposes activation through [Transfer Playback](https://developer.spotify.com/documentation/web-api/reference/transfer-a-users-playback).

Remaining priorities:

| Priority | Finding and user impact | Suggested change |
| --- | --- | --- |
| High | Spotify progress is generated by a local timer. The browser host does not forward `player_state_changed`, while `PlayerSession` advances the queue only on `EngineStatus.ENDED`. Now Playing can disagree with Spotify, and queued Spotify songs do not advance reliably. See `DesktopPlaybackEngine.kt:109`, `JvmSpotifyWebPlaybackHost.kt` SDK listeners, and `PlayerSession.kt:65`. | Feed SDK position, pause state, track identity, and track-end transitions into the playback engine. For external devices, use bounded Web API polling only while Spotify playback is active. Test remote pause, completion, reconnect, and switching providers. |
| High | Connect fallback chooses the first speaker if there is no active device or computer. Startup is attempted only when the entire device list is empty. During inspection, the API returned three inactive speakers and no computer, so this branch would skip local startup. See `SpotifyProvider.kt`, `resolvePlaybackTarget`. | Add a device selector and remember the user's choice. Prefer the Kainos player or an explicitly chosen local device. Do not silently transfer audio to an arbitrary speaker. |
| High | Removing the playing queue item changes the queue's current index without changing the engine's track. The highlighted song can be wrong, and the replacement may be skipped when the old song ends. See `QueueScreen.kt:66` and `QueueController.kt:62`. | Route queue removal and clearing through `PlayerSession`, with tests for deleting the current, preceding, and final items while playing. |
| High | Android's ExoPlayer listener does not implement `onPlayerError`, so failed URLs or local media do not publish `EngineStatus.FAILED` and cannot trigger the existing fallback path. See `AndroidPlaybackEngine.kt:50` and `PlayerSession.kt:68`. | Forward Media3 errors into engine state with a useful message. Verify a failed URL triggers fallback or a visible terminal error. |
| High | The Now Playing favorite flag survives a track change. A newly selected unfavorited song can inherit the previous song's filled heart. See `PlayerSession.kt:180` and `NowPlayingScreen.kt:221`. | Derive the heart from the current track ID and `LibraryRepository.favoriteIds`, eliminating duplicate favorite state. |
| High | App favorites, remembered tracks, and recent history live only in `MutableStateFlow`. Restarting Kainos loses them. See `data/library/LibraryRepository.kt:9`. | Persist the user's library state with atomic writes and reload it on startup. Keep Spotify account data distinct from app favorites. |
| Medium | Spotify liked songs appear under Songs, but Albums and Artists are built solely from local files. These tabs can display sample content even after Spotify loaded successfully. See `LibraryScreen.kt:78` and `LibraryScreen.kt:94`. | Derive albums and artists from the combined library, preserving provider references. Show a clear empty state when there is no content. |
| Medium | Missing or unreadable music folders are silently skipped, and refresh exceptions are discarded. An unmounted drive therefore looks like an empty library. See `JvmLocalTrackSource.kt:35` and `AppContainer.kt`, `refreshLocalLibrary`. | Return scan diagnostics alongside tracks. Show the unavailable root and allow retry while retaining readable files. |
| Medium | The web player launches an external browser app window and depends on its DRM support and audio-activation rules. It is not an embedded native audio player. Browser startup failures and activation need to be visible in Kainos itself. See `JvmSpotifyWebPlaybackHost.kt`, `launchBrowserLocked`. | Expose web-player state and recovery actions in Settings/Now Playing. Decide whether a browser window is acceptable before investing in an embedded browser runtime. The official Spotify desktop client's installed help says its minimized-start flag works only on Windows. |

Two further usability improvements are worth scheduling. Search requests and receives albums and artists, but renders only tracks and playlists despite its placeholder promising all three. Render those results or change the placeholder. Desktop metadata probing is serial and can take up to three seconds per slow file; cache probe results by file path, size, and modification time before adding bounded concurrency. See `SearchScreen.kt:132`, `UnifiedSearch.kt:66`, `JvmLocalTrackSource.kt:117`, and `LocalAudioProbe.kt:70`. The scan slowdown is a code-derived worst case, not a measured scan benchmark.

Validation completed: 94 JVM tests passed, desktop Kotlin compilation passed, Android debug APK assembly passed, and `git diff --check` passed. No claim is made that all Spotify playback limitations are resolved.
